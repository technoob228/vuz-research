# Монитор конкурсных списков

Рабочий монитор для РЭУ. Данные — публичный REST API сайта конкурсных списков
`abitrating.rea.ru` (Supabase). В базе 235 582 записи по 956 конкурсным группам.

## Поля, которые отдаёт API

`unique_code_profile` (код абитуриента), `competitive_group_id`, `rating` (позиция),
`priority` (приоритет), `sum_mark` (баллы), `agreement` (согласие), `contract` (договор),
`application_status`, плюс справочник групп с `admission_volume` (число мест) и
`place_type_name` (Общий конкурс / Контракт).

Этого достаточно для полной симуляции зачисления.

## Файлы

| Файл | Что делает |
|---|---|
| `rea_fetch.py` | Клиент API: поиск по коду, справочник групп |
| `dump.py` | Полная выгрузка базы в `entrants.json` + `groups.json` (~2 мин) |
| `simulate.py` | Разбор одной группы: кто выше уйдёт, кто останется |
| `cascade.py` | Итеративная симуляция (deferred acceptance) по всем группам |

## Запуск

```bash
echo "<anon-key>" > rea.key     # ключ берётся из JS-бандла abitrating.rea.ru
python3 rea_fetch.py 2260794    # статус по коду
python3 dump.py                 # выгрузка базы
python3 cascade.py 2260794      # симуляция
```

Ключ намеренно не хранится в репозитории.

## Ограничение, которое надо помнить

Симуляция видит **только РЭУ**. Межвузовский отток (люди уходят в ВШЭ, МГУ и другие)
не учитывается, поэтому расчёт даёт **нижнюю, пессимистичную оценку** — реальные шансы выше.
Чтобы закрыть этот пробел, нужны парсеры остальных вузов и склейка по коду абитуриента —
если код единый (выдаётся Суперсервисом), склейка сработает.

## Что дальше

1. Парсеры ВШЭ, РАНХиГС, Бауманки, ЦУ — по той же схеме (искать XHR-запросы в devtools).
2. Cron каждые 15–30 мин + запись снапшотов с меткой времени → история и скорость оттока.
3. Телеграм-алерты при смене прогноза.

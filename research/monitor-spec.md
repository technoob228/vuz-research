# Реалтайм-монитор шансов на поступление: техспека

Идея: собирать публичные конкурсные списки всех вузов, склеивать заявки одного человека по уникальному коду и симулировать зачисление — чтобы видеть не «моя позиция 171 из 69 мест», а «из 170 человек выше реально претендуют 55, я прохожу».

## Почему это вообще возможно

Конкурсные списки 2026 года по приказу Минобрнауки № 821 содержат по каждой строке:

- уникальный код поступающего (ФИО нет)
- сумму баллов и разбивку по предметам + индивидуальные достижения
- **приоритет** этой программы у данного абитуриента (1–5)
- **отметку о согласии** на зачисление
- льготы / преимущественное право

Обновляются не реже 5 раз в сутки. Это ровно тот набор полей, из которого считается исход.

## Ключевая гипотеза (проверить первой)

**Одинаков ли код абитуриента в списках разных вузов.** Если код выдаётся Суперсервисом «Поступление в вуз онлайн» (Госуслуги) — он единый, и тогда работает вся кросс-вузовская склейка. Если каждый вуз генерит свой — остаётся только внутривузовская симуляция (тоже полезная, но слабее).

Проверка за 5 минут: взять свой код и поискать его в списках другого вуза. Наблюдение владельца задачи: коды повторяются на нескольких платформах — то есть гипотеза, скорее всего, верна.

## Что даёт склейка

Обычный калькулятор считает «позиция против мест» — усреднённая оценка. Склейка даёт покодовый расчёт: для каждого, кто выше, видно, уйдёт он или останется.

| Ситуация конкурента выше | Вывод |
|---|---|
| Приоритет 4 здесь, приоритет 1 в другом вузе, где проходит с запасом | Уйдёт, место освободится |
| Подал согласие в другом вузе | Уже ушёл, список просто не обновился |
| Приоритет 1 здесь + согласие | Останется гарантированно |
| Приоритет 1 здесь, но не проходит по баллам | Останется в списке, места не займёт |

## Архитектура

```
сборщик (cron, каждые 15–30 мин)
  ├─ парсеры вузов: ВШЭ (Мск/СПб), РЭУ, РАНХиГС, Бауманка, ЦУ
  │    единый выход: {код, вуз, программа, баллы, приоритет, согласие, позиция}
  └─ снапшот в БД с меткой времени

движок симуляции (после каждого сбора)
  ├─ склейка строк по коду → профиль абитуриента (все его заявки)
  ├─ итеративное зачисление (deferred acceptance / Гейл–Шепли):
  │    повторять до стабилизации:
  │      для каждой программы взять топ-N по баллам с учётом ВПП (согласие)
  │      если человек зачислен по более высокому приоритету —
  │      вычеркнуть его из всех списков с приоритетом ниже
  │      пересчитать границы
  └─ выход: прогноз проходного балла и позиции по каждой программе

фронтенд
  ├─ «где прохожу прямо сейчас» по всем программам
  ├─ история позиции: график по дням
  ├─ рекомендация по расстановке приоритетов
  └─ телеграм-алерты при смене статуса
```

## Реализация по шагам

1. **Парсеры** — самое трудоёмкое: у каждого вуза свой формат (HTML-таблица, XLSX, JSON за фронтендом). Начинать с сетевой вкладки браузера: часто список тянется отдельным JSON-запросом, который дёргается напрямую. Один вуз ≈ 30–60 минут.
2. **Хранилище** — SQLite достаточно. Таблица `snapshots(код, вуз, программа, баллы, приоритет, согласие, позиция, ts)`. История нужна для динамики и скорости оттока.
3. **Движок** — алгоритм отложенного принятия, 50–100 строк. Это в точности то, что делает сам Суперсервис при зачислении.
4. **Фронт** — один HTML-файл (как `postuplenie.html`) + автообновление.
5. **Алерты** — телеграм-бот: «позиция на АиУД поднялась на 12», «прогноз: проходишь», «прогноз изменился».

## Сроки: трезво

Полноценный сервис — 2–3 дня. До дедлайна 5 августа 12:00 их нет. Реалистичный план:

- **Сегодня–завтра, 2–3 часа:** парсер только под 3–5 программ, которые реально в игре + проверка гипотезы о едином коде. Даже без склейки видно главное: **сколько человек выше подали согласие**. Если из 170 выше согласие подали 40 — место практически есть.
- **4 августа:** прогон симуляции, финальное решение по приоритетам.
- **5 августа до 12:00:** подача согласия.

Полную версию достроить **после** кампании: пригодится в следующем году и как портфолио-проект.

## Границы: что законно, а что нет

Конкурсные списки — официально публикуемые открытые данные, вузы обязаны их публиковать; они обезличены. Сбор и анализ таких списков — то, чем занимаются десятки сервисов (vuzopedia, «Поступашки»).

**Не переходить:**
- не сопоставлять коды с реальными людьми (соцсети, чаты, утечки) — это уже обработка персданных без основания;
- не публиковать собранную базу целиком;
- уважать нагрузку на сайты: интервал 15–30 минут более чем достаточен (списки чаще 5 раз в сутки не обновляются).

Инструмент для собственного решения — нормально. Сервис, показывающий «кто эти люди» — нет.
